# NetIntel AI Suite

**Three machine learning components for network operations: unsupervised anomaly detection on traffic telemetry, alert correlation, and reinforcement learning for SD-WAN path selection.**

[![CI](https://github.com/MarckMorris/netintel-ai-suite/actions/workflows/ci.yml/badge.svg)](https://github.com/MarckMorris/netintel-ai-suite/actions/workflows/ci.yml)
[![Python](https://img.shields.io/badge/python-3.10%20%7C%203.11%20%7C%203.12-blue)](https://www.python.org/)
[![License](https://img.shields.io/badge/license-MIT-green)](LICENSE)

Each component addresses a different part of the same operational problem: too
much telemetry, too many alerts, and too many decisions that get made by rule of
thumb. A Streamlit dashboard sits over all three.

## Honesty about what this is

A personal project. Nothing here has run against a live network. Every dataset
in this repository is synthetic, generated by
`project1_anomaly_detection/data/synthetic_network_logs.py`, and re-validating any
model on real telemetry is a prerequisite for taking its output seriously.

No performance claim is made in this README, because none has been measured on
anything real. The previous version of this file carried an "expected impact:
70% reduction in false positives" line that came from nowhere; it is gone.

## Components

### Alert correlation — the part that works with no ML at all

A single fault produces dozens of alerts: the interface drops, BGP tears down,
the tunnel flaps, the monitoring system pages three times. This engine groups
alerts by the gap between them and labels a group with a root cause when its
alert types match a known failure signature.

```python
from correlation_engine import AlertCorrelationEngine

engine = AlertCorrelationEngine()
incidents = engine.correlate_alerts(alerts_dataframe)
print(engine.reduction_ratio(alerts_dataframe))   # measure it on YOUR alerts
```

Three design decisions worth naming:

- **Clustering is on the gap between consecutive alerts**, not on distance from the first alert in the group. A ten-minute storm stays one incident instead of being chopped into fixed windows.
- **Alerts matching no rule are returned, not dropped**, as single-alert incidents with an `UNCORRELATED` root cause. An alert that silently disappears is how an outage gets missed.
- **Rules can require a partial match.** The AAA rule fires on two of its three symptoms, because a client may never reach 802.1X if RADIUS is already timing out.

`reduction_ratio()` reports how much less an operator has to read. It is a
function you run on your own alert stream, not a number this README asserts.

### Anomaly detection

An LSTM autoencoder trained only on clean traffic, flagging sequences it cannot
reconstruct. Unsupervised, so no labelled attack data is needed.

The telemetry generator produces a per-minute series with a real daily and
weekly shape — two weekday peaks, a broader weekend lift — then injects uplink
failures with a realistic recovery curve rather than a step change. Faults are
labelled, so an unsupervised model can still be scored.

Requires TensorFlow: `pip install -r requirements-anomaly.txt`.

### SD-WAN path optimiser

A Gymnasium environment where an agent picks one uplink per step and is rewarded
for latency, loss, utilisation and cost together. Packet loss is weighted
hardest, because a lossy path breaks applications that a merely slow path only
annoys.

Requires PyTorch and Stable-Baselines3: `pip install -r requirements-sdwan.txt`.

## Quick start

```bash
git clone https://github.com/MarckMorris/netintel-ai-suite.git
cd netintel-ai-suite

python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt   # core + test tooling, no TensorFlow

pytest                                 # 73 tests, about 3 seconds
```

Generate the datasets — they are not committed, because they are ~900 KB of
output that this script reproduces byte-for-byte from a fixed seed:

```bash
python project1_anomaly_detection/data/synthetic_network_logs.py
```

## Dependencies are layered

Installing this used to pull TensorFlow, PyTorch, transformers and
sentence-transformers — several gigabytes — before you could read a 200-line
correlation engine. It no longer does.

| File | Pulls | For |
| --- | --- | --- |
| `requirements.txt` | pandas, numpy, scikit-learn, gymnasium | correlation engine, SD-WAN environment, data generator |
| `requirements-dev.txt` | + pytest, flake8, black | the test suite |
| `requirements-anomaly.txt` | + TensorFlow | LSTM autoencoder |
| `requirements-sdwan.txt` | + PyTorch, Stable-Baselines3 | DQN agent |
| `requirements-api.txt` | + FastAPI, uvicorn | inference service |
| `requirements-dashboard.txt` | + Streamlit, plotly | dashboard |

`sentence-transformers`, `transformers`, `networkx`, `seaborn`, `matplotlib` and `redis`
were removed: nothing imported them. The correlation engine used to load a 90 MB
sentence-transformer model on construction and never call it.

## Testing

```bash
pytest                      # 73 tests
pytest -m "not slow"        # skip anything needing TensorFlow or PyTorch
pytest --cov=. --cov-report=term-missing
```

Tests that need an optional heavy dependency skip themselves rather than fail,
so CI installs only the core requirements and finishes in seconds. CI also
regenerates both datasets from the seed on every push, which is what makes it
safe to keep generated CSVs out of git.

The tests worth reading are the ones that pin behaviour that fails silently:

- `test_sdwan_env.py::TestSeeding` — `reset(seed=...)` used to do nothing, because the environment drew from the global `np.random` instead of `self.np_random`. No RL result in this repository was reproducible until that was fixed.
- `test_telemetry_generator.py::test_output_is_reproducible` — the generator used `datetime.now()` as its start, so two runs with the same seed never matched.
- `test_correlation_engine.py::TestUncorrelatedAlerts` — nothing gets dropped.

## Known limitations

- Synthetic data only. The traffic model is a plausible shape, not a measurement.
- No production deployment and no real-network validation.
- The correlation rules are hand-written and cover three failure signatures. Real deployments need many more, tuned to their own alert vocabulary.
- The DQN agent is trained against the simulator, so its policy reflects the simulator's assumptions and nothing else.
- The three components share no data model; they are three studies in one repository, not one integrated pipeline.
